Why distributed is hard

Part 1 of 8 · the failure model you design against

On one machine a call either returns or the whole process dies. Across machines a third outcome appears: you do not know. Everything else on this page is a way of living with that.

The failure model

Why distributed is hard

State the failures you tolerate before you pick a protocol. A design is only "correct" relative to a failure model.

FailureWhat happensTypical causeStandard defence
Crash-stopNode halts and never returnsHardware loss, terminated instanceReplication, failover
Crash-recoveryNode halts, later returns with its disk state but not its memoryRestart, deploy, OOM killDurable log (fsync before ack), rejoin protocol
OmissionA message is never sent or never receivedFull queue, dropped packet, overloaded receiverTimeouts, retries, idempotency
Network partitionTwo groups of healthy nodes cannot talk to each otherSwitch or link failure, misconfiguration, zone isolationMajority quorums, fencing
Timing ("slow is the new down")Node responds, but far too late; often partially (one disk, one endpoint)GC pause, noisy neighbour, degraded disk, overloadDeadlines, circuit breakers, hedging, outlier ejection

  • Datacentre designs assume crash-recovery plus omission plus partitions, with checksums to turn data corruption into a detectable crash-like fault.
  • Slow nodes are harder than dead ones: a dead node is removed by health checks, a slow one keeps receiving traffic and holds its callers' threads.

Interview tip: say "I am assuming non-Byzantine failures: nodes may crash, pause or be partitioned, but do not lie". It shows you know the assumption exists.

The fallacies of distributed computing

Partial failure and timeouts

Why distributed is hard

A timeout tells you only that no reply arrived in time. The request may never have arrived, may be still running, or may have completed with the reply lost. The caller cannot tell these apart.

  • A timeout is an unknown outcome, not a failure. The safe reactions are: retry an idempotent operation, or query the outcome, or surface "pending" to the user.
  • A failure detector built on timeouts is necessarily imperfect: short timeouts declare healthy nodes dead (false positives, needless failovers), long ones leave dead nodes in rotation.
  • Hence the two recurring tools: idempotency, so retrying is safe, and fencing, so a node wrongly declared dead cannot do damage when it wakes.

Two generals and FLP

Why distributed is hard

Two generals. Two parties that can only talk over a link that may drop messages cannot become certain that they both agreed, however many messages they exchange. Whoever sent the last message does not know whether it arrived, and adding an acknowledgement only moves the doubt to the acknowledgement. This is why a sender can never know for sure that a receiver processed a message, and why "exactly-once delivery" is not on offer.

FLP (Fischer, Lynch, Paterson, 1985). In a fully asynchronous system, where there is no bound on message delay or process speed, no deterministic consensus protocol can guarantee that it always terminates if even one process may crash.

  • FLP is about liveness, not safety. Raft and Paxos never decide two different values; what they cannot promise is to decide within bounded time under arbitrary delays.
  • Real systems step around it by assuming partial synchrony: timeouts (with randomisation) make progress very likely once the network behaves for a while.

Senior signal: phrase guarantees as "always safe, live when a majority can communicate in a timely way". That is exactly what consensus systems provide.

Time and order

Part 2 of 8 · deciding what happened first

There is no shared clock. Ordering events across machines needs either logical clocks, which capture causality, or a single sequencer, which imposes an order.

  • Physical clocks: why wall-clock timestamps cannot order events
  • Lamport clocks: one counter, consistent with causality
  • Vector clocks: detecting concurrent updates
  • Hybrid clocks and TrueTime: physical time with guarantees
  • Total order vs partial order
  • Idempotent sequence numbers: order and dedup on one stream

Physical clocks

Time and order

Quartz clocks drift, typically by tens of parts per million (10 ppm is about 0.9 s per day; Google's Spanner design assumes a worst case of 200 ppm). NTP corrects this to within roughly a millisecond inside a well-run datacentre and tens of milliseconds or worse over the internet, and may step the clock backwards while doing so. All figures are order of magnitude.

  • Two clocks per machine: time-of-day (can jump, use only for display and coarse TTLs) and monotonic (never goes back, use for durations and timeouts, meaningless across machines).
  • Wall-clock timestamps are fine for logs, metrics and TTLs measured in seconds. They are unsafe for ordering writes, lock expiry decided by two different machines, and "newest wins" conflict resolution.
  • Process pauses (GC, VM migration) make it worse: a thread can read the clock, pause for seconds, then act on the stale reading.

Failure mode: last-write-wins with client or server timestamps loses acknowledged writes under clock skew. If you propose LWW, say what data you are prepared to lose.

Lamport clocks

Time and order

One integer per node. Increment it on every local event and send; on receive set it to max(local, received) + 1. Attach it to every message.

Tells youDoes not tell you
If a happened before b (causally), then L(a) < L(b)L(a) < L(b) does not imply a happened before b: they may be concurrent
A total order when ties are broken by node id: (L, node)Whether two events are concurrent, or how far apart they were in real time

Cost: 8 bytes per message. Use it when you need some deterministic order consistent with causality (ordering log entries, tie-breaking); Raft terms and Paxos ballot numbers are the same idea.

Vector clocks

Time and order

One counter per node, carried as a vector. Increment your own slot on each event; on receive take the element-wise maximum, then increment your own slot.

Tells youDoes not tell you / costs
Exactly whether a happened before b, b before a, or they are concurrentWhich concurrent write should win: that is an application merge or a sibling returned to the client
Enough to detect conflicting updates without losing eitherSize grows with the number of participants; needs pruning, which can produce false conflicts
  • Where it shows up: Dynamo-style stores track version vectors (a close relative, one entry per replica rather than per client) to detect concurrent writes to a key. The original Dynamo paper returns conflicting versions to the application to merge.
  • Trade-off: Lamport is small and gives an order but hides concurrency; vectors reveal concurrency but cost O(nodes) per value.

Hybrid clocks and TrueTime

Time and order

Hybrid logical clock (HLC). A timestamp of (physical time, logical counter) that advances like a Lamport clock but stays within the clock-skew bound of wall time, so it is fixed size, respects causality across messages, and is still meaningful to a human. Databases such as CockroachDB, YugabyteDB and MongoDB use HLC-style timestamps for versioning and snapshot reads.

TrueTime (Spanner). The clock API returns an interval [earliest, latest] that is guaranteed to contain the true time, with the width kept to a few milliseconds by GPS and atomic clock references in each datacentre. Spanner waits out that uncertainty before a commit becomes visible ("commit wait"), so if transaction T1 finishes before T2 starts, T1's timestamp is smaller: timestamp order matches real-time order.

ClockSizeRespects causalityDetects concurrencyRelated to real time
Wall clock (NTP)8 bytesNoNoApproximately, unbounded error in the worst case
Lamport8 bytesYesNoNo
VectorO(nodes)YesYesNo
HLC8 to 12 bytesYesNoYes, within the assumed skew bound
TrueTime-style interval2 timestampsYes, by waiting out uncertaintyNoYes, with an explicit error bound

Trade-off: without bounded-uncertainty clocks, an HLC database must handle the skew window some other way (for example restarting a read that hits an uncertain timestamp, or refusing to run when skew exceeds a configured maximum). Exact behaviour is implementation-dependent.

Total order vs partial order

Time and order

Partial orderTotal order
DefinitionSome pairs of events are incomparable (concurrent)Every pair is ordered, and every node sees the same order
SourceCausality: happens-before, vector clocksA single sequencer: one leader's log, one partition, a consensus log
CostNo coordination; conflicts must be mergedEvery write goes through one place; throughput and availability of that place bound the system

  • Delivering the same messages in the same order to all nodes (total order broadcast) is equivalent in power to consensus. If a design needs a global order, it needs a consensus-backed log or a single leader somewhere.
  • The practical compromise is total order per key: order within a partition, none across partitions. See ordering guarantees and partition keys.

Idempotent sequence numbers

Time and order

On a single stream you do not need a clock at all. The sender numbers its messages (sender id, sequence number) and the receiver remembers the highest number applied per sender. That gives order, duplicate detection and gap detection with one integer of state per sender.

  • Where it shows up: TCP sequence numbers; Kafka's idempotent producer (producer id, epoch and a per-partition sequence number, with the broker rejecting duplicates and out-of-sequence batches); replication streams keyed by log offset.
  • Requirement: the receiver must store "last applied sequence" atomically with the effect, otherwise a crash between the two reintroduces the duplicate.
  • Limit: it covers one sender-receiver stream. For arbitrary clients retrying arbitrary requests, use idempotency keys.

Leader election and leases

Agreement

Why a leader: a single writer gives a total order for free, removes write conflicts and makes invariants (uniqueness, balances) easy to check. The cost is that the leader is a throughput ceiling and its failure needs detection and handover.

Lease-based election: a node becomes leader by writing itself into a strongly consistent store with an expiry ("I am leader until T"). It renews well before T (for example every third of the lease). If it stops renewing, another node may take the lease only after it expires.

ChoiceShort lease (1 to 5 s)Long lease (30 s or more)
Failover timeFastSlow: the system is leaderless until expiry
False failoversMore: a GC pause or a network blip loses the leaseFewer
Load on the lease storeHigher renewal rateLower
  • A lease is a timing assumption: it is safe only if clocks advance at roughly the same rate on both sides and the holder notices expiry before acting. Holders should stop work some margin before their local view of the expiry.
  • The lease store itself must be consensus-backed (etcd, ZooKeeper, a database with a compare-and-set on a single row). A lease in an asynchronously replicated store can be granted twice after a failover.

Failure mode: the leader pauses for longer than the lease (stop-the-world GC, VM freeze, swapped-out process), a new leader is elected, then the old one resumes and carries on writing. A lease alone cannot prevent this; the next chapter does.

Fencing tokens

Agreement

Every time the lease or lock is granted, the lock service also returns a number that only ever increases. The holder sends that number with every write, and the resource rejects any write whose number is lower than the highest it has seen.

  • Where the token comes from: a Raft term, a ZooKeeper zxid or znode version, an etcd revision, a database sequence, a leader epoch in Kafka.
  • What it costs: the protected resource must be able to compare and remember tokens, atomically with the write. A plain file system or a third-party API usually cannot, and then the lock is only best-effort.
  • The same idea under other names: epoch numbers, generation numbers, If-Match version checks, STONITH (which fences by powering the old node off instead).

Senior signal: whenever you say "we take a lock" or "the leader does X", follow it with "and the writes carry the epoch so a stale holder is rejected". Interviewers probe exactly this.

Consensus in plain terms

Agreement

Consensus lets a group of nodes agree on a value so that the decision survives crashes and is never contradicted. Run it repeatedly and you get an agreed, ordered log; feed the same log to the same deterministic state machine on every node and you get a replicated database, lock service or config store.

PropertyMeaningKind
AgreementNo two nodes decide different valuesSafety: holds always
ValidityThe decided value was proposed by some nodeSafety
IntegrityA node decides at most onceSafety
TerminationEvery non-faulty node eventually decidesLiveness: only when a majority is up and can communicate in a timely way
  • Use it for: small, critical, low-churn state: who is leader, shard maps, configuration, locks, the metadata of a larger system.
  • What you pay: every write needs a majority round trip and a durable write on each (roughly 1 to 10 ms in one region, an inter-region round trip when the group spans regions), and the group is unavailable for writes without a majority.
  • You almost never implement it. You use etcd, ZooKeeper, a Raft library or a database built on one, and you say so.

Raft: roles and terms

Agreement

Raft keeps a replicated log through a single strong leader. Every node is in one of three roles, and time is divided into numbered terms, each with at most one leader.

  • Term: a monotonically increasing number stored durably on each node and sent in every RPC. It is a logical clock and a fencing token: requests carrying an older term are rejected.
  • One vote per term: a node votes for at most one candidate in a given term (the vote is persisted before replying). Since winning needs a majority, two leaders in one term are impossible.
  • Followers are passive: they only answer RPCs. Clients talk to the leader; a follower redirects.
  • Two RPCs carry the whole protocol: RequestVote and AppendEntries (which doubles as the heartbeat when empty).

Raft: log replication and commit

Agreement

  • Consistency check: each AppendEntries names the index and term of the entry just before the new ones. A follower that has no matching entry refuses; the leader steps back one entry at a time (or faster with an optimisation) until they match, then overwrites the follower's conflicting suffix. The leader never rewrites its own log.
  • Commit rule: an entry is committed once it is stored on a majority and it belongs to the leader's current term. Entries from earlier terms are never committed by counting replicas; they become committed indirectly when a current-term entry after them commits.
  • Durability: nodes persist term, vote and log entries before replying, so a committed entry survives any minority of crashes.
  • Client retries: a leader can crash after committing but before replying, so commands should carry a client id and serial number and the state machine should deduplicate.
  • Reads: a leader that has been deposed without knowing it would serve stale data from local state. Linearizable reads therefore go through the log, or confirm leadership with a round of heartbeats to a majority first, or rely on a leader lease (which reintroduces a clock assumption).

Raft: leader election

Agreement

  • Election timeout: each follower picks a random timeout (the paper suggests 150 to 300 ms; production systems often use around a second) and restarts it on every valid heartbeat. Randomisation makes it likely that one node times out first and wins before the others start.
  • Split vote: if no candidate reaches a majority, candidates time out, increment the term and try again with fresh random timeouts.
  • Election restriction: a voter refuses a candidate whose log is less up to date than its own (compare the term of the last entry, then the log length). Because a committed entry is on a majority and a winner needs votes from a majority, the new leader always holds every committed entry.
  • Timing requirement for liveness: broadcast time must be much smaller than the election timeout, which must be much smaller than the mean time between failures. Safety does not depend on timing.
  • Common extensions, named in one breath: pre-vote (a partitioned node does not disrupt the cluster with an inflated term when it returns) and membership change one server at a time or through joint consensus.

Raft under a partition

Agreement

  • Majority side: stops hearing heartbeats, elects a leader in a higher term, keeps serving writes.
  • Minority side: the old leader still accepts requests but can never commit them, so clients time out. A local read on this side can be stale unless reads are confirmed with a majority.
  • On heal: the old leader sees term 4, steps down, and its uncommitted entries are overwritten by the new leader's log. Nothing that was acknowledged to a client is lost, because nothing on the minority side was acknowledged.
  • No majority anywhere (for example a 2 / 2 / 1 split of five): no side can elect a leader and the cluster is unavailable for writes until connectivity returns. This is the CP choice.

Interview tip: the two questions asked most are "can there be two leaders?" (yes, briefly, in different terms; only the newer can commit) and "can a committed write be lost?" (no, given durable storage and at most a minority failed).

Paxos in one paragraph

Agreement

Single-decree Paxos agrees on one value in two phases. A proposer picks a unique, increasing proposal number and asks acceptors to prepare; each acceptor promises to ignore lower numbers and reports any value it has already accepted. If a majority promises, the proposer sends accept with the value of the highest-numbered proposal reported, or its own value if none was, and the value is chosen once a majority accepts. Multi-Paxos repeats this per log slot and keeps a stable leader so the prepare phase is skipped in the common case, which makes it behave much like Raft. The honest summary: Paxos and Raft tolerate the same failures at similar cost; the original Paxos description leaves log management, leader election and membership change to the implementer, so real "Paxos" systems differ from each other, while Raft specifies those parts. In an interview, know the two phases and the majority overlap argument, and do not offer to implement either.

Quorums and why majorities

Agreement

Any two majorities of the same group share at least one node. So a new leader's voters always include someone who saw the last committed decision, and two sides of a partition can never both make progress. To survive f crash failures you need 2f + 1 nodes.

NodesMajorityFailures toleratedComment
110No fault tolerance
220Worse than 1: either node failing stops writes
321The usual minimum; one node per zone
431Same tolerance as 3, slower commits
532Survives one failure during maintenance of another
743Rare: more replicas to wait on per write
  • Even sizes add cost without adding tolerance. Use 3 or 5; scale reads with non-voting learners or followers, not with more voters.
  • Losing a majority permanently means manual recovery with possible data loss. Spread voters across at least three failure domains.
  • Dynamo-style quorums (N replicas, W write acks, R read replies, R + W > N) guarantee that a read set overlaps the latest successful write set. That is not the same as linearizability: concurrent writes, partially failed writes and sloppy quorums can still produce stale or conflicting reads. Details in Data Systems.

Split brain

Agreement

Two nodes each believe they are the leader and both accept writes. The histories diverge, and merging them afterwards is usually manual and lossy (duplicate ids, double spends, overwritten rows).

PreventionHow it worksCost / caveat

Witness / tiebreakerA small third voter (often in a third zone) that holds no dataOne more thing to run; still must be a real voter

Failure mode: a two-node primary and standby pair where the standby promotes itself when it "cannot see" the primary. A partition between them (with both still reachable by clients) gives two primaries. A timeout is never proof of death.

Coordination services

Agreement

ZooKeeper (Zab protocol), etcd and Consul (both Raft) are small, strongly consistent key-value stores with leases or sessions and watches. They exist so that applications do not implement consensus themselves.

Gossip protocols

Agreement

Every node periodically (about once a second) picks a few random peers and exchanges what it knows. Information spreads like an epidemic: with fan-out k, all N nodes hear a rumour in O(log N) rounds, with no coordinator and no single point of failure.

GainPay
Scales to thousands of nodes, constant load per nodeOnly eventual: for a few rounds nodes disagree about the state
Tolerates node loss and message loss without special handlingRedundant messages; state must be mergeable (versioned per node)
No leader, no quorum, works during partitionsCannot be used to make a decision that needs agreement (who is leader, who owns a lock)

Where it shows up: cluster membership and metadata in Dynamo-style stores and Cassandra, Redis Cluster's cluster bus, Consul's Serf layer (SWIM-based). Each entry carries a version or heartbeat counter so that the newer one wins on merge.

The dual-write problem

Distributed transactions

A service writes to its database and then to a second system (broker, cache, search index, another service) as two separate steps. Nothing makes the pair atomic, so any crash or timeout between them leaves the two permanently different.

Order of the two writesFailure in between gives
DB commit, then publishLost event: downstream never hears of a real change
Publish, then DB commitPhantom event: downstream acts on a change that was rolled back
Either order, two concurrent requestsThe two systems may apply the updates in different orders and end on different values, with no failure at all

Senior signal: spot every dual write in your own diagram ("write DB, then update cache", "save, then call the email service") and name the fix: one source of truth plus a derived, replayable stream (outbox / CDC), not "we will wrap it in a try/except".

Two-phase commit

Distributed transactions

A coordinator asks every participant to prepare (do the work, write it durably, hold the locks, promise to commit if told to). If all vote yes it records the decision and tells everyone to commit; any no or timeout means abort.

PropertyDetail
GivesAtomic commit across participants: all commit or all abort
BlockingA prepared participant cannot decide alone; rows stay locked for as long as the coordinator is down
LatencyTwo round trips and several forced log writes, with locks held throughout
AvailabilityNeeds every participant and the coordinator up: availability multiplies down
Does not giveIsolation across participants by itself; that comes from each participant's locks or MVCC
  • Where it is still used: XA transactions between a database and a broker or between two databases; inside distributed SQL databases, where a transaction spanning shards is committed with 2PC and each participant (and the coordinator state) is itself a consensus group, which removes the single-coordinator blocking problem (Spanner is the documented example); Kafka transactions use a coordinator-driven protocol of the same shape.
  • Avoid across independently owned microservices: it couples their availability, needs every party to support the protocol, and holds locks across network calls.
  • Three-phase commit adds a pre-commit phase so participants can decide without the coordinator, but it assumes bounded delays and no partitions, so it is rarely deployed.

Sagas

Distributed transactions

A saga is a sequence of local transactions, one per service, each committed on its own. If a later step fails, the earlier ones are undone by compensating transactions. You get atomicity "eventually" and give up isolation.

StepServiceLocal transactionCompensationKind
1OrderCreate order as PENDINGMark order REJECTEDCompensable
2InventoryReserve stockRelease reservationCompensable
3PaymentCapture paymentNone needed if it fails; refund if a later step could failPivot: the go / no-go point
4OrderMark order CONFIRMEDNoneRetriable: must eventually succeed
5ShippingCreate shipmentNoneRetriable
  • Compensation is a new business transaction, not a rollback: a refund, a cancellation, a reversing ledger entry. The original remains visible in history.
  • Compensations and retriable steps must be idempotent and must be retried until they succeed; a compensation that can fail permanently needs a human queue.
  • Put steps that cannot be undone (charging a card with fees, sending an email, shipping) at or after the pivot, and make everything after the pivot unable to fail for business reasons.
  • Each step is "commit locally and emit a message", which is itself a dual write: build sagas on the outbox.

Trade-off: use a saga when the steps belong to different services and seconds of visible intermediate state are acceptable. Avoid it when the invariant must hold at every instant (a balance that may never go negative across two accounts): put that data in one database instead.

Saga choreography

Distributed transactions

No central controller. Each service subscribes to the others' events and reacts, including to failure events.

  • Gain: no extra component, loose coupling, each team owns its reactions.
  • Pay: the workflow is implicit, spread over subscriptions; hard to answer "where is order 981 stuck"; easy to create cyclic event dependencies; timeouts have no natural owner.
  • Reasonable for two to four steps with a linear flow. Beyond that, orchestrate.

Saga orchestration

Distributed transactions

One orchestrator owns the workflow as a persisted state machine. It sends commands, waits for replies, and on failure issues compensations in reverse order.

  • Gain: the flow is explicit and testable, timeouts and retries live in one place, participants stay simple (command in, reply out).
  • Pay: one more service to run and scale; risk of business logic drifting into the orchestrator; its state store must be durable and its commands idempotent, since it retries after a crash.
  • Often delegated to a workflow engine (Temporal, AWS Step Functions, Camunda) rather than hand-built.

What isolation a saga loses

Distributed transactions

Each local transaction commits and is visible immediately, so other requests can observe and act on a saga that is half done or about to be compensated.

Transactional outbox and CDC

Distributed transactions

Turn the dual write into a single local transaction: write the business row and a row describing the event into an outbox table in the same database transaction. A separate relay then publishes outbox rows to the broker.

Relay styleHowTrade-off
Polling publisherQuery unpublished outbox rows every N ms, publish, mark as sentSimple, any database; adds polling load and latency; ordering needs care with concurrent transactions
Log-based CDCTail the database's replication log (Debezium-style connectors)Low latency, commit order preserved, no polling; more infrastructure and operational knowledge
  • Guarantee: at-least-once publication, in commit order per aggregate. Consumers must deduplicate on the event id (the inbox pattern).
  • Costs: an extra write per transaction, a relay to run and monitor (lag is your new SLI), outbox cleanup, and events arrive milliseconds to seconds after commit.
  • CDC directly on business tables (no outbox) also works, but couples consumers to your schema; the outbox lets you publish a deliberate event contract.
  • Failure mode: with log-based CDC on PostgreSQL, a stalled connector holds a replication slot and the WAL grows until the disk fills. Alert on slot lag.

Try-confirm-cancel

Distributed transactions

A reservation protocol at the business level. Try reserves the resource in each service (hold funds, hold a seat) without making it final; Confirm turns every reservation into the real thing; Cancel releases them.

  • Versus a saga: nothing is shown as done until Confirm, so there is less to compensate and better isolation; the price is that every participant must expose three idempotent operations and model holds explicitly.
  • Holds carry an expiry so an abandoned transaction frees itself. Confirm must not fail for business reasons, only be retried.
  • Failure modes to handle: a Cancel that arrives before its Try (record it and make the late Try a no-op), and duplicates of any of the three.
  • Where it shows up: payment authorise then capture, ticket and hotel holds, inventory reservations.

Delivery semantics

Messaging correctness

SemanticsHow you get itWhat can happenFits
At-most-onceSend without retry, or acknowledge before processingLoss, never duplicatesMetrics samples, best-effort notifications
At-least-onceRetry until acknowledged; acknowledge after processingDuplicates, never loss (while the broker is durable)The default for anything that matters
Effectively-once (exactly-once processing)At-least-once delivery plus an idempotent or deduplicating consumer, or an atomic commit of "result and progress marker" togetherMessage may be delivered and even executed twice, but the observable effect happens oncePayments, ledgers, counters
  • Exactly-once delivery is impossible over an unreliable channel: it is the two generals problem. The sender either retries (duplicates possible) or does not (loss possible).
  • What products mean by "exactly-once": Kafka's exactly-once semantics combine the idempotent producer with transactions that atomically write output records and consumer offsets, which gives effectively-once for read-process-write loops that stay inside Kafka. A side effect outside it (an email, a call to another service, a row in an external database) is not covered and still needs its own idempotency.
  • Acknowledge after the effect is durable. Acknowledging first silently turns at-least-once into at-most-once.

Interview tip: never say "we use exactly-once delivery". Say "at-least-once delivery with idempotent consumers, so processing is effectively-once", then say where the dedup state lives.

Idempotency keys

Messaging correctness

An operation is idempotent if doing it twice has the same effect as doing it once. Where the operation is not naturally so (charge a card, create an order), the client attaches a unique key per logical operation and the server remembers key to outcome.

Retry findsServer does
No rowInsert IN_PROGRESS and execute
COMPLETED, same request hashReturn the stored response without executing
IN_PROGRESS, lock not expiredReturn a conflict (commonly 409) so the client retries later; do not execute concurrently
IN_PROGRESS, lock expiredTake over: ask the downstream for the outcome using the same derived key, then finish
Same key, different request hashReject (commonly 422 or 400): the key was reused for another operation
  • Atomicity is the whole point: the key row and the business effect commit in the same local transaction. A dedup record in one store and the effect in another is a dual write.
  • Propagate: every downstream call uses a key derived from the original, so the chain is idempotent end to end.
  • Retention: keep keys longer than the longest client retry window (24 hours is a common public-API choice), then expire. Storage is one small row per write request.
  • Scope the key per tenant or user so one client cannot collide with another.
  • Prefer natural idempotency when available: PUT with a full representation, "set status = SHIPPED", an upsert on a business key, a conditional write on a version.

Failure mode: "check if the key exists, then insert" as two statements. Two concurrent retries both pass the check. Use an insert against a unique constraint, or a conditional put, as the single atomic step.

Ordering guarantees and partition keys

Messaging correctness

A partitioned log orders messages within a partition and promises nothing across partitions. You choose what is ordered by choosing the key.

What breaks per-key orderGuard
Producer retries with several requests in flightIdempotent producer with sequence numbers (Kafka preserves order with idempotence on and at most 5 in-flight requests per connection)
Consumer processes a partition with a thread poolSerialise per key inside the consumer (hash key to a worker), or process sequentially
Changing the partition countKey-to-partition mapping changes: old and new events of a key sit on different partitions. Over-provision partitions up front or migrate deliberately
Retry topic or dead-letter queueThe failed message is overtaken by later ones of the same key: block the key, or make handlers tolerate reordering with versions
Rebalance during processingTwo consumers may briefly process the same partition: handlers must be idempotent
  • Key choice: the entity whose events must be ordered (account, order, device). Too coarse a key (tenant) creates hot partitions; too fine a key loses the order you needed.
  • Global order needs one partition, which caps throughput at one partition's rate and one consumer. Almost always per-entity order is what the business actually requires.
  • Belt and braces: put a per-entity version in each event so a consumer can detect and drop a stale or out-of-order update.

The inbox pattern

Messaging correctness

The consumer-side mirror of the outbox. The consumer records each message id in an inbox table in the same transaction as the state change it causes. A redelivered message hits the unique constraint and is skipped.

  • Outbox + at-least-once broker + inbox is the standard recipe for effectively-once processing between two services with their own databases.
  • Storage: one row per message for the dedup window. The window must exceed the longest possible redelivery delay (broker retention, DLQ redrive); prune older rows.
  • If the handler's effect is not in a database (calls an API, sends an email), pass the message id on as an idempotency key instead; if the target does not support one, you are back to at-least-once and should say so.
  • Cheaper alternative when it fits: store "last processed offset or sequence per partition" with the state, as in sequence numbers.

Poison messages and dead-letter queues

Messaging correctness

A poison message fails every time it is processed (bad schema, a bug, a reference to deleted data). With naive at-least-once it is redelivered forever, and on an ordered partition it blocks everything behind it.

  • Classify errors: timeouts and 503s are transient (retry with backoff); validation and deserialisation errors are permanent (dead-letter at once, retrying wastes capacity).
  • Carry context: original topic, partition and offset, attempt count, error, first-failure time. Without it the message cannot be diagnosed or redriven.
  • Operate it: alert on DLQ depth and age, provide a redrive tool, and make redrive safe by keeping consumers idempotent.
  • Trade-off: dead-lettering one message lets later messages of the same key overtake it. If per-key order is a correctness requirement, either stop the partition and page someone, or park all later messages of that key too.

Retries, backoff and jitter

Messaging correctness

Retries turn transient failures into successes and turn overload into an outage. The rules exist to keep the first effect and prevent the second.

RuleWhy
Retry only idempotent operationsA timeout does not mean the first attempt failed
Retry only retryable errorsTimeouts, connection resets, 503, 429 (after Retry-After). Never 400, 401, 403, 404, 422
Exponential backoffGive a struggling dependency progressively more room
JitterClients that failed together otherwise retry together, in synchronised waves that re-create the spike at 100 ms, 200 ms, 400 ms
Retry at one layerThree attempts at each of three layers is up to 27 attempts at the bottom
Retry budgetCap retries as a fraction of normal traffic (for example 10 percent per client) so retries cannot multiply load during an outage
  • Retry storm: a dependency slows, callers time out and retry, offered load rises exactly when capacity is lowest, and the dependency cannot recover even after the original cause is gone. This self-sustaining state is called a metastable failure.
  • Retry budget mechanics: a token bucket per client refilled by successful requests; each retry spends a token; with no tokens, fail immediately. gRPC's retry throttling and service-mesh retry budgets work this way.
  • Servers help by answering overload with an explicit "do not retry" or Retry-After, and by rejecting cheaply.

Senior signal: whenever you add "with retries" to an arrow, add in the same sentence: idempotent, capped, jittered, and bounded by a budget and the request deadline.

Timeouts and deadline propagation

Messaging correctness

Every remote call needs a timeout, and a chain of calls needs a shared one. The edge sets an absolute deadline; every hop forwards the time remaining, checks it before starting work and abandons work once it has passed.

  • Choosing a timeout: start from the dependency's measured p99 or p99.9 plus headroom, not a round number. Too long and threads pile up behind a slow dependency; too short and healthy requests fail and trigger retries.
  • Separate connect timeout (short, tens to hundreds of ms inside a datacentre) from request timeout.
  • Inner timeouts must be shorter than outer ones, otherwise the outer caller gives up first and the inner work is wasted. Deadline propagation enforces this automatically.
  • gRPC carries the deadline in request metadata and cancels downstream calls for you; with plain HTTP you pass a header and enforce it yourself.
  • Propagate cancellation as well as the deadline, so that a client disconnect stops downstream work.

Circuit breaker

Staying up

A client-side state machine in front of a dependency. When calls keep failing it stops making them for a while, which protects the caller's resources and gives the dependency room to recover.

SettingTypical choiceWhy it matters
Trip conditionError or slow-call rate above about 50 percent over a 10 to 30 s rolling window, with a minimum request countA raw count trips on low traffic; no minimum trips on one bad call

Bulkhead

Staying up

Partition resources so that a failure in one compartment cannot sink the others. Give each dependency, tenant or request class its own bounded pool.

Rate limiting and load shedding

Staying up

Both reject requests. They answer different questions and belong in different places.

Rate limitingLoad shedding
QuestionIs this client within its allowance?Can this server finish more work right now?

Backpressure

Staying up

When a consumer is slower than its producer, the slowness has to go somewhere. Backpressure sends it upstream as a signal to slow down, instead of letting it accumulate in a buffer.

MechanismExample
Bounded queue, block or reject when fullThread pool with a fixed queue and a rejection policy
Window or credit based flow controlTCP receive window, HTTP/2 flow control, Reactive Streams request(n)
Pull instead of pushKafka consumers fetch at their own pace; the durable log is the buffer and consumer lag is the signal
Explicit slow-down response429 or 503 with Retry-After
  • An unbounded queue is not a buffer, it is a latency and memory leak: it hides overload until the process runs out of memory, and everything in it is already late.
  • Backpressure only works where the source can slow down (batch jobs, internal producers, streams). A human at a browser cannot, so at the edge backpressure becomes load shedding.
  • Queues smooth bursts; they do not fix a sustained rate mismatch. If average arrival exceeds average service rate, the only fixes are more capacity or less work.

Hedged requests and tail latency

Staying up

With fan-out, rare slowness becomes common: if one backend is slow 1 percent of the time, a request that needs 100 backends hits at least one slow response 63 percent of the time (1 - 0.99100). The tail of the dependency becomes the median of the caller.

  • Numbers: in "The Tail at Scale" (Dean and Barroso), hedging a BigTable read after 10 ms cut the 99.9th percentile from about 1800 ms to 74 ms for about 2 percent more requests.
  • Safe only for idempotent operations, normally reads. Hedging a non-idempotent write needs an idempotency key.
  • Cap it: hedges are extra load, so give them a budget (a few percent of traffic) and disable them when the backend reports overload. Unbounded hedging during an incident is a retry storm.

Distributed locks

Coordination patterns

First ask what the lock is for. Efficiency: avoid doing the same work twice; an occasional double run costs a little money. Correctness: a double run corrupts data. A best-effort lock is fine for the first and wrong for the second.

Why the single-node Redis lock is unsafe for correctnessWhat happens
Lease expiry while the holder is paused or slowThe holder passes its expiry without noticing (GC, stalled I/O, slow network), another client acquires, and both act. No TTL value fixes this.
Asynchronous replicationThe primary fails before the lock key reaches the replica; after failover a second client acquires the same lock
No fencing tokenThe random value identifies the holder but is not ordered, so the resource cannot tell old from new

The Redlock debate. Redlock acquires the lock on a majority of several independent Redis nodes within a validity window; Martin Kleppmann argued that its safety rests on timing assumptions (bounded clock drift, process pauses and network delay) and that it issues no fencing token, so it should not be used where correctness depends on the lock. Salvatore Sanfilippo (Redis's author) replied that those assumptions are reasonable in practice and that the lock's unique value can be used for compare-and-set on the resource; the disagreement is about system models, and neither side claims it replaces fencing at the resource for strict correctness.

Safer alternativeHowCost
Fencing token checked by the resourceLock service issues an increasing token; storage rejects older ones (fencing tokens)Resource must support the check

Leader-follower work assignment

Coordination patterns

One elected leader decides which worker owns which shard, partition or task. Workers do not negotiate with each other; they heartbeat and obey.

  • Gain: one place makes placement decisions, so balancing, draining a node and prioritising are simple and globally informed.
  • Pay: the leader must be elected and fenced; reassignment after a worker death waits for the failure detector; a rebalance can pause work.
  • Handover rule: the new owner of a shard starts only after the old owner's lease on it has expired or been explicitly released, and writes are fenced by epoch in case that rule is violated by a pause.
  • Where it shows up: Kafka's controller and consumer-group coordinator, HDFS NameNode with DataNodes, the GFS and Bigtable masters, most job schedulers.
  • Keep the leader off the data path: it hands out assignments, clients cache them and talk to workers directly.

Sharded workers with consistent hashing

Coordination patterns

No per-task assignment at all: every node computes the owner of a key from the membership list. Adding or removing a worker moves only about 1/N of the keys.

  • Use when there are many small, similar units of work (per-user timers, per-device sessions, cache shards) and central assignment would be a bottleneck.
  • Virtual nodes (100 or more points per worker) even out the load and spread a departed worker's keys across all survivors. Rendezvous hashing is a simpler alternative with the same minimal-movement property. Ring mechanics are in Building Blocks.
  • Failure mode: if membership is gossiped, two workers can hold different views for a few seconds and both believe they own a key. Either make the work idempotent, or take membership from a consensus store and fence by its version.
  • Hashing balances key count, not load: a hot key still overloads its owner.

Linearizability vs serializability

Consistency in practice

Two different guarantees that are constantly confused. One is about recency of single operations across replicas, the other about isolation of multi-operation transactions.

LinearizabilitySerializability
AboutSingle operations on a single object (a register, a key)Transactions: groups of operations over many objects
PromiseEach operation appears to take effect at one instant between its start and its end; the system behaves like one copyThe result equals that of running the transactions one at a time in some order
Real-time orderYes: once a write has returned, every later read sees itNo: the equivalent serial order need not match wall-clock order, so a stale snapshot is allowed
Belongs toReplication. The "C" in CAPConcurrency control. The "I" in ACID
PreventsStale reads, two leaders both acquiring a lock, uniqueness violations across replicasLost updates, write skew, dirty and non-repeatable reads
Typical mechanismConsensus or a single leader with synchronous replication; reads confirmed by a quorumTwo-phase locking, serializable snapshot isolation, single-threaded execution
PriceLatency of a quorum round trip; unavailable on the minority side of a partitionAborts and retries, or lock waits and deadlocks
  • Strict serializability is both together: serializable, and the serial order respects real time. Spanner calls its version external consistency.
  • A serializable database read through asynchronous replicas is still serializable but not linearizable. A linearizable key-value store without multi-key transactions is not serializable.
  • Many databases default to something weaker than serializable (read committed or snapshot isolation). Check the default before relying on it.

Interview tip: "do you need linearizability?" is answered by finding the invariant: locks, leader election, unique usernames and "never oversell the last seat" need it; timelines, counters and catalogues do not.

Eventual consistency tactics

Consistency in practice

"Eventually consistent" only promises that replicas converge if writes stop. These are the mechanisms that actually make them converge, and decide what they converge to.

TacticWhat it doesLimit
Read repairOn a read, compare replica versions and write the newest back to stale replicasOnly heals data that is read
Anti-entropyBackground process compares replicas (commonly with Merkle trees, so only differing ranges are transferred) and syncs themI/O cost; convergence time depends on how often it runs
Hinted handoffAnother node holds writes meant for an unreachable replica and replays them when it returnsA hint is not a replica: it improves availability, not durability
Conflict resolutionLast-write-wins, application merge of siblings, or CRDTsLWW silently drops concurrent writes and trusts clocks

CRDTs. Conflict-free replicated data types are structures (counters, sets, registers, sequences) whose merge is commutative, associative and idempotent, so replicas that have seen the same updates in any order, any number of times, reach the same state without coordination. They cost extra metadata (per-replica counts, tombstones) and cannot enforce invariants that need agreement, such as "balance never below zero" or "at most one winner".

Read-your-writes

Consistency in practice

After a user changes something, that user must see the change, even though replicas lag. Other users may see it later. This is much cheaper than linearizability and is what most products need.

OptionHowTrade-off
Read own data from the leaderRoute reads of things the user can edit (own profile, own orders) to the primarySimple; fails if most reads are of editable data
Leader for a window after a writeFor N seconds after a user writes, send that user's reads to the primary (flag in session or cookie)N must exceed replication lag; wrong when lag spikes
Version tokenThe write returns a log position or timestamp; the client sends it with reads; a replica serves only if it has applied that position, otherwise waits or forwards to the primaryPrecise, works across devices if the token is stored server-side per user; needs replica support
Sticky routingPin the user to one replicaGives monotonic reads (no going back in time); gives read-your-writes only if that replica has the write; breaks on failover
Quorum or synchronous readsRead from enough replicas to overlap the write set, or replicate synchronouslyHigher latency on every read or write
Client-side echoThe UI shows what the user just submitted from local stateCosmetic: a reload or another device shows the truth
  • Related session guarantees worth naming: monotonic reads (a user never sees data go backwards) and consistent prefix (never a reply before the message it answers).
  • The same problem appears with caches and search indexes: after a write, the user's next read must bypass or wait for the derived store.

Which guarantee do I actually need?

  • Five sentences to have ready: a timeout is an unknown outcome; delivery is at-least-once so handlers are idempotent; a lease can be held twice so writes are fenced; a majority is needed for anything that must not diverge; pick the weakest consistency that preserves the invariant.
