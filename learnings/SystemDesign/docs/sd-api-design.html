API and Communication Design

The "API" step of a design interview, and everything that travels over it: how to get from requirements to endpoints in two minutes, which style and transport to pick, the details interviewers probe (pagination, idempotency, versioning, webhooks), real-time delivery, service-to-service calls, and the security that sits on every one of them. Designing an API in an interview

Part 1 of 6 · from requirements to endpoints

The API step is a contract, not a catalogue. Spend about two minutes, write 4 to 6 calls that cover the core use cases, and let them drive the data model and the high-level design that follow.

Requirements to endpoints in two minutes

Designing an API in an interview

Turn each functional requirement into a noun and a verb, then write one line per call. Stop when the core flows are covered.

  • Resources: the things users create and read (account, transfer, message). They usually become your tables too.
  • Operations: one line each, METHOD /path. Only the calls the requirements need.
  • Request / response: the 3 to 5 fields that matter. Identity comes from the token, never from the body.
  • Errors: name the two or three that are specific to the domain (insufficient funds, duplicate request).
  • Cross-cutting: say once, in one sentence: "all calls are authenticated, writes take an idempotency key, lists are cursor-paginated".

Interview tip: say which style you are using and why in one breath ("REST over HTTPS for the public API, gRPC between services"), then move on. Do not design every CRUD endpoint.

Worked example: a bank-transfer API

Designing an API in an interview

Requirements: move money between accounts, see a transfer's status, list an account's history. This is the whole API sketch you would write on the board.

  • The create call returns pending: settlement is asynchronous, so the status resource is part of the contract from the start.
  • The idempotency key is required, not optional: a retried payment is the first thing an interviewer will ask about. See Idempotency for writes.
  • available vs ledger balance signals you know holds and pending entries exist.

Error format

Designing an API in an interview

One error shape for the whole API. A common standard is Problem Details (RFC 9457, media type application/problem+json); a house format is fine if it carries the same things.

  • Stable machine code (insufficient_funds) that clients branch on; the human text can change freely.
  • Request id echoed in a header and the body, the join key into logs and traces.
  • Field-level list for validation errors, so a form can show all problems at once.
  • No internals: no stack traces, SQL, hostnames, or "user exists" hints on login and reset endpoints.

gRPC and Protocol Buffers

API styles

An RPC framework: a .proto contract generates typed clients and servers in many languages; calls run as HTTP/2 streams with binary Protobuf payloads. Use it inside the data centre; keep REST or GraphQL at the edge.

  • Why it suits service-to-service: compact payloads (often several times smaller than JSON), generated typed stubs, multiplexing on long-lived connections, streaming, and first-class deadlines and cancellation that propagate down the call chain.
  • Schema evolution: add fields with new numbers; unknown fields are ignored by old readers. Never change a field's type or number.
  • Failure mode: a layer 4 load balancer pins a long-lived HTTP/2 connection to one backend, so load never rebalances. Use layer 7 (per-request) balancing or client-side balancing; see Building Blocks.
  • You pay: not human-readable, no HTTP caching, browsers need gRPC-Web through a proxy.

GraphQL

API styles

The client sends a query naming exactly the fields it wants across a typed graph; one round trip replaces several REST calls. It fixes over-fetching (fat responses a mobile client throws away) and under-fetching (call 1 for the list, then N calls for details).

Where it hurtsWhyMitigation
HTTP cachingOne endpoint, POST, a different shape per queryPersisted queries (hash sent with GET), client-side normalised cache, per-field cache hints
Rate limitingOne request can cost 1 or 10,000 database readsQuery cost analysis, depth and complexity limits, limit by cost not by request count
AbuseDeeply nested or aliased queriesDepth limit, timeout, allowlist of persisted queries for first-party clients
AuthorizationMany paths reach the same objectEnforce in the data layer per object and field, not per query
ObservabilityEverything is POST /graphql with 200Metrics per operation name and per resolver

When each is the right answer

API styles

  • REST: the default for anything public. Everyone can call it, debug it with curl, and cache it.
  • gRPC: internal calls where latency, typing and streaming matter and you control both ends.
  • GraphQL: product APIs with many client teams and fast-changing views. Avoid for simple CRUD, public partner APIs and file transfer.
  • WebSocket / SSE: only where the server must speak first. See Real-time communication.

Pagination

API details that get probed

Default to cursor (keyset) pagination for anything large or changing. Offset is acceptable only for small, mostly static lists that need "jump to page N".

Offset: ?limit=50&offset=100000Cursor / keyset: ?limit=50&cursor=...
QueryORDER BY created_at DESC LIMIT 50 OFFSET 100000WHERE (created_at, id) < (:t, :id) ORDER BY created_at DESC, id DESC LIMIT 50
Cost of a deep pageScans and discards 100,000 rows: O(offset)Index seek: O(page size), the same at any depth
Rows inserted while pagingItems shift: duplicates or skipped rowsStable: continues from the last key seen
Jump to page N, total countYesNo (next / previous only)
Sharded dataEach shard must return offset + limit rowsEach shard seeks from the key, results are merged
  • The cursor is the last row's sort key, base64-encoded and opaque (sign or encrypt it if clients must not forge it). Opaque means you can change the scheme later.
  • The sort key must be unique and immutable: add id as a tie-breaker to a timestamp.
  • Enforce a maximum limit (say 100) on the server. Skip total_count unless required: it is a full scan.

Filtering and sorting

API details that get probed

  • Allowlist the filterable and sortable fields: every one needs a supporting index. Arbitrary filters are an accidental full table scan and a denial-of-service vector.
  • Simple equality and ranges as query parameters; complex search belongs in a dedicated POST /search backed by a search index, not in the primary store.
  • fields= (sparse fieldsets) trims payloads without adopting GraphQL.
  • A cursor is only valid for the filter and sort it was issued with: encode them in the cursor or reject a mismatch.

Idempotency for writes

API details that get probed

A client that times out cannot know whether the write happened. Retries are therefore mandatory, and the server must make a repeated request have the effect of one.

MethodSafe (no state change)IdempotentRetry blindly?
GET, HEAD, OPTIONSYesYesYes
PUT (full replace)NoYesYes
DELETENoYes (second call may return 404)Yes
PATCHNoDepends: "set x = 5" yes, "x += 5" noOnly with a key or If-Match
POSTNoNoOnly with an idempotency key
  • Key: a client-generated UUID per logical operation, scoped to the caller, kept for a window (commonly 24 hours).
  • Same key, different body: store a request hash and reject the mismatch (422 or 409). Same key, still in flight: return 409 or wait, never run twice.
  • Natural keys work too: a unique constraint on (merchant_id, order_id) is an idempotency key the business already has.
  • Retry only on timeouts, connection errors, 429 and 5xx, with exponential backoff and jitter. Retry storms are covered in Distributed Systems Patterns.

Failure mode: checking the key in a cache first and writing later. Two concurrent retries both miss and both execute. The uniqueness check must be atomic with the write.

  • Default to PATCH with merge-patch semantics for user-edited resources.
  • Prevent lost updates with optimistic concurrency: the client sends If-Match: "etag", the server returns 412 if the resource changed. See HTTP caching.

Bulk and long-running operations

API details that get probed

Anything that can exceed a few seconds (export, video transcode, bulk import, settlement) should not hold a request open. Accept the job, return a status resource, finish in the background.

  • Bulk writes: cap the batch size, and choose all-or-nothing (one transaction) or partial success with a per-item result list (an overall 200 or 207 plus item-level statuses). Say which.
  • Give each item its own idempotency key or client id so a retried batch does not double-apply.
  • Large uploads bypass the API: hand out a pre-signed object-store URL, with multipart / resumable upload for big files.

Webhooks

API details that get probed

A webhook is your API calling the customer's: an HTTP POST per event to a URL they registered. It replaces polling, and it makes you a client of an unreliable server you do not control.

ConcernDesign
SigningHMAC-SHA256 over timestamp + "." + raw_body with a per-endpoint secret, sent in a header; receiver compares in constant time. Support two active secrets for rotation.
Replay protectionReject timestamps outside a tolerance (about 5 minutes) and event ids already seen.
RetriesExponential backoff with jitter over hours to days; then a dead-letter state, an alert, and auto-disable of endpoints that keep failing.
OrderingNot guaranteed. Include a sequence number or updated_at; or send thin events ("transfer tr_9x changed") and let the receiver fetch current state.
RecoveryA GET /events?after= API so receivers can reconcile after an outage, plus manual redelivery.
Provider safetySender-side SSRF protection (block private address ranges), per-endpoint timeouts and concurrency so one slow customer cannot stall the rest.

Rate limits and quotas

API details that get probed

From the API's side, a limit is part of the contract: documented, visible in headers, and answered with a clear 429. The algorithms (token bucket, sliding window) are in Building Blocks.

Rate limitQuota
WindowSeconds to minutesDay or month

  • Limit on several dimensions: per key, per tenant, per endpoint class (a search costs more than a read), and a global ceiling.
  • Header names vary: X-RateLimit-* is the long-standing convention, RateLimit-* the IETF draft. Retry-After is the one clients actually obey.

Compression and payload size

API details that get probed

  • Negotiate: the client sends Accept-Encoding: br, gzip, the server answers with Content-Encoding. JSON typically shrinks by 70 to 90 percent.
  • Skip tiny bodies (under about 1 KB, where the overhead outweighs the gain) and already-compressed media. Compression costs CPU; do it at the edge where possible.
  • Shrink before you compress: pagination, sparse fieldsets, no embedded blobs (return a URL), a binary format for internal hops.
  • Cap sizes: a maximum request body (413 beyond it), a maximum page size, a maximum decompressed size to stop decompression bombs.
  • On mobile networks the payload size often dominates latency; that is the argument for field selection and for HTTP/2 or 3 header compression.

API gateway and Backend-for-Frontend

API details that get probed

A gateway is the single entry point that handles what every API needs. A Backend-for-Frontend (BFF) is a thin per-client API that shapes and aggregates data for one kind of front end.

API gatewayBFF
DoesTLS termination, authentication, rate limiting, routing, request ids, logging, canary routingAggregates several service calls, trims and reshapes payloads, handles client-specific flows

Contract-first design and SDKs

API details that get probed

Write the contract (OpenAPI for REST, .proto for gRPC, the schema for GraphQL) before the code, review it like code, and generate server stubs, client SDKs, docs, mocks and a breaking-change check in CI from that one file.

Short polling and long polling

Real-time communication

  • Arithmetic: 1 million clients polling every 5 s is 200,000 requests per second of mostly empty responses. That number is why you move off short polling.
  • Long polling needs a server that can hold many idle requests cheaply (async I/O), and a hold time below every proxy's idle timeout.

Server-Sent Events and WebSocket

Real-time communication

  • SSE first when only the server pushes: it is plain HTTP, so auth, gateways, HTTP/2 multiplexing and CDNs keep working. Client-to-server traffic uses normal POSTs. Over HTTP/1.1 browsers cap it at about 6 connections per origin.
  • WebSocket when the client also sends often (typing, cursors, game input) or you need binary frames.
  • Neither gives delivery guarantees. Add message ids, acks and resume-from-id at the application level.

Scaling WebSocket connections

Real-time communication

The problem is not throughput, it is state: each user is pinned to one server, and a message for them can arrive at any other. Separate the stateful connection tier from stateless business logic and join them with pub-sub.

Push notifications

Real-time communication

When the app is in the background there is no socket of yours to write to. The operating system keeps one shared connection to its vendor's push service; you ask that service to deliver.

  • Device token: issued by the OS per app install, registered with your back end, can change; the provider's response reports invalid tokens, which the workers prune.
  • Best effort: no delivery guarantee, no ordering; providers may throttle, collapse (collapse key) or drop expired messages. Payloads are small (about 4 KB).
  • Design consequence: push is a hint ("you have new messages"), the app then syncs over your API. Never make push the source of truth.
  • Dedupe per user and event, respect preferences and quiet hours, and rate limit per user before the queue.

Interview tip: a long synchronous chain is a red flag. Ask of every hop: "does the user need this answer before we respond?" If not, publish an event.

Request-reply over a queue

Service-to-service communication

When you want the buffering of a queue but still need an answer: send the request with a correlation id and a reply address, and match the reply when it arrives.

  • Use for slow, bursty or rate-limited back ends (pricing engines, document rendering) where you want backpressure and worker scaling.
  • Avoid for low-latency lookups: you have rebuilt RPC with more moving parts. If the requester blocks waiting, you keep the temporal coupling and lose the simplicity.

Event schema and versioning

Service-to-service communication

  • id for consumer dedupe (delivery is at-least-once); subject + sequence for per-entity ordering; occurred_at is event time, not processing time; trace_id ties the hops together.
  • An event is a public API. Consumers you have never met depend on it, and old events sit in the log for days or forever, so readers must handle every version still retained.
  • Evolve additively: new optional fields with defaults only. For a real break, publish a new type (payment.captured.v2) alongside the old one and migrate consumers.
  • Schema registry with compatibility checks in CI (backward: new readers read old data; forward: old readers read new data) stops a producer deploy from breaking consumers.
  • Thin vs fat: thin events (ids only) force a callback but are never stale; fat events (full state) decouple consumers but spread data, including PII, everywhere.

Service mesh and sidecars

Service-to-service communication

A mesh moves network concerns out of application code into a proxy deployed next to every service instance (the sidecar), configured centrally by a control plane.

You getHow
mTLS everywhereShort-lived workload certificates issued and rotated by the control plane; service identity, not IP addresses
Traffic policyTimeouts, retries with budgets, circuit breaking, per-request load balancing, canary and traffic splitting
ObservabilityUniform request metrics (rate, errors, latency), access logs and trace spans for every hop, in any language
Authorization"Service A may call B's /transfers" as policy

Trade-off: two extra proxy hops per call (typically around a millisecond in total, more at the tail), extra CPU and memory per instance, and a complex system to operate. Worth it with many services in several languages; overkill for five services where a shared library does the job. Sidecar-less (per-node) meshes reduce the overhead.

Timeouts, retries and deadlines

Service-to-service communication

One-line pointers; the full treatment is in Distributed Systems Patterns.

  • Timeout: every network call has one, set from the callee's p99, not left at a library default of "forever".
  • Retry: only idempotent calls, only on retryable errors, with exponential backoff, jitter and a retry budget; retry at one layer, not every layer (3 retries at 3 layers is 27 calls).
  • Deadline: an absolute time passed down the chain so every hop knows the remaining budget and abandons work nobody is waiting for.
  • Circuit breaker: stop calling a failing dependency and fail fast or degrade.
  • Backpressure and load shedding: reject early (429 / 503) rather than queue without bound.

Authentication vs authorization

Security on the wire

Authentication (authn) answers "who are you?" and fails with 401. Authorization (authz) answers "may you do this to that object?" and fails with 403 (or 404 to hide existence).

  • The gateway can check coarse rules (valid token, required scope). Only the owning service can check "does account 42 belong to this caller".
  • Internal services must not trust a bare X-User-Id header: pass a signed token or rely on mTLS identity plus a propagated, verifiable user context.

JWT: anatomy, validation, expiry and revocation

Security on the wire

  • Validate, in order: algorithm against an allowlist (never trust alg from the token, reject none); signature with the key for kid from the issuer's JWKS (cached); iss; aud; exp and nbf with a small clock skew; then scopes.
  • Prefer asymmetric signing (RS256, ES256, EdDSA): services verify with a public key and cannot mint tokens. A shared HMAC secret lets every verifier forge.
  • Keep PII and secrets out of the payload; keep it small.

OAuth 2.0 authorization code with PKCE

Security on the wire

OAuth 2.0 is delegated authorization: a user lets an app call an API on their behalf without giving the app their password. Authorization code with PKCE is the flow for web, mobile and single-page apps.

  • PKCE (proof key for code exchange) defeats authorization-code interception: a stolen code is useless without the verifier. Required for public clients (mobile, SPA), recommended for all.
  • state ties the callback to the request (CSRF protection); redirect URIs are matched exactly against a registered list.
  • Scopes limit what the token can do; the API still enforces object-level authorization.
  • The implicit flow and the password grant are deprecated: do not propose them.

Client credentials and OpenID Connect

Security on the wire

When there is no user, a service authenticates as itself with the client credentials grant.

  • Client authentication can be a secret, a signed assertion (private_key_jwt) or mTLS; prefer the last two over long-lived shared secrets.
  • When a service acts for a user, propagate the user's context (token exchange or a signed internal token) so downstream authorization still sees the real principal.
  • OpenID Connect in one line: an identity layer on OAuth 2.0 that adds an ID token (a JWT saying who logged in, for the client) next to the access token (for the API), which is what "Sign in with ..." uses.

API keys and when they are enough

Security on the wire

An API key is a long random secret that identifies a calling application or account, not a user.

Enough whenNot enough when
Server-to-server calls from a customer's back endActing on behalf of an end user (use OAuth)

  • Send in a header, never in the URL (URLs end up in logs and referrers).
  • Store only a hash; show the key once; give it a recognisable prefix (sk_live_) so secret scanners can find leaks.
  • Scope keys (read-only, per environment), allow several active keys for rotation, support expiry and optional IP allowlists.
  • For high-value calls, add request signing (HMAC over method, path, body and timestamp) so a captured request cannot be altered or replayed.

TLS and mTLS

Security on the wire

TLS gives confidentiality, integrity and server authentication. Mutual TLS (mTLS) adds a client certificate, so each side proves its identity; it is the standard for service-to-service traffic.

  • Ephemeral key exchange gives forward secrecy: stealing the server's key later does not decrypt recorded traffic.
  • Where TLS ends matters: terminating at the load balancer leaves the internal hop in plain text. Re-encrypt to the back end, or use a mesh, for zero-trust networks.
  • mTLS cost is operational: issuing, rotating and revoking certificates for every workload. Use short-lived certificates (hours to days) issued automatically.
  • mTLS authenticates the service. It says nothing about the end user, so it complements tokens rather than replacing them.

  • Why envelope: bulk data never goes to the KMS (which is slow and rate limited); a DEK per object or tenant limits the blast radius; rotating the KEK means re-wrapping small DEKs, not re-encrypting terabytes.

  • Use authenticated encryption (AES-GCM or ChaCha20-Poly1305). Never invent a scheme.

Password storage

Security on the wire

Passwords are never encrypted and never stored with a fast hash. Store the output of a salted, deliberately slow, memory-hard password hash.

  • Algorithm: Argon2id preferred; bcrypt or scrypt are acceptable. Not MD5, SHA-1 or plain SHA-256: those run at billions of guesses per second on GPUs.
  • Salt: unique and random per user, stored with the hash. It defeats rainbow tables and makes identical passwords look different.
  • Work factor: tune to roughly 100 ms or more per hash on your hardware, and raise it over time. That cost is also why login needs its own rate limit.
  • Pepper (optional): a secret kept in the KMS, applied to all hashes, so a database dump alone is not enough.
  • Around it: rate limit and lock out per account and per IP, check against breached-password lists, offer MFA or passkeys, give identical responses for "no such user" and "wrong password".

Secrets management

Security on the wire

  • Where: a secrets manager or vault, fetched at start-up or injected at deploy time by workload identity. Not in source control, container images, or logs.
  • Prefer no secret: workload identity (cloud IAM roles, mesh certificates) removes static credentials altogether.
  • Short-lived and dynamic: database credentials issued per service instance with a TTL beat a shared password that never changes.
  • Rotation without downtime: accept old and new together for a window (two active keys), then retire the old one. Design every credential for this from day one.
  • Least privilege and audit: each service reads only its own secrets; every read is logged.
  • Leak response: secret scanning in CI and on push, and a rehearsed revoke-and-rotate procedure. A leaked secret is rotated, not "removed from git history".

Input validation and least privilege

Security on the wire

  • Validate at the boundary against a schema: types, lengths, ranges, formats, enums. Allowlist what is valid instead of blocklisting what is bad; reject unknown fields on writes.
  • Validate again where it matters: business invariants (balance never negative) live in the service and the database constraints, not only in the gateway or the client.
  • Bound everything: body size, array length, string length, nesting depth, page size, request time.
  • Least privilege: each service gets its own identity, its own database user limited to its tables, network policy limited to the services it calls, and tokens scoped to the operations it needs.
  • Defence in depth: assume one layer fails. The gateway authenticates, the service authorizes, the database user cannot drop tables, the network blocks the rest.

Multi-tenancy isolation

Security on the wire

The tenant id comes from the authenticated token, never from a request parameter, and is applied to every query, cache key, queue and object path by a shared layer (or database row-level security) rather than by each developer remembering a WHERE clause. Choose the isolation level by risk and cost: shared tables with a tenant column (cheapest, weakest), a schema or database per tenant, or a dedicated stack for the largest or most regulated tenants, with per-tenant rate limits and quotas so one noisy tenant cannot starve the rest.

Audit logging and PII handling

Security on the wire

Audit log: an append-only record of security-relevant actions: who (user, service, on whose behalf), did what, to which object, when, from where, with what outcome, and the request id. It is separate from debug logs, write-once, access-controlled, and retained per policy.

API review checklist

  • Shape: resources are nouns, methods carry the verbs, ids are opaque, one casing, UTC timestamps, money in minor units.
  • Identity: caller and tenant come from the token; every object access is authorized for that caller.
  • Writes: each write is idempotent by nature or by key; behaviour on timeout and retry is defined.
  • Reads: lists are paginated with a cursor and a server-side maximum; filters and sorts are allowlisted and indexed.
  • Errors: correct status class, one error format, stable machine codes, request id, no internals leaked.
  • Slow work: anything over a few seconds is a job with a status resource.
  • Limits: rate limits, quotas, payload and page caps, timeouts, all documented and visible in headers.
  • Caching: each GET is deliberately cacheable, private or no-store; ETags where clients revalidate or edit.
  • Evolution: changes are additive; versioning and deprecation policy are stated; the contract is the source of truth.
  • Real time: the push channel is the simplest that meets the latency number, with reconnect and resume.
  • Between services: timeouts and deadlines everywhere, retries bounded, async where the user is not waiting, events versioned.
  • Security: TLS on every hop, least-privilege scopes, input validated against a schema, secrets in a manager, PII minimised and masked, sensitive actions audited.
