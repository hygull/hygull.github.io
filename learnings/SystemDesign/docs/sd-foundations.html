Functional vs non-functional requirements

The interview framework

Functional: what the system does ("a user can post", "followers see the post"). Non-functional: how well it does it (scale, latency, availability). Functional requirements pick the boxes; non-functional requirements pick how many, where and with which guarantees.

Non-functionalQuestion to askWhat the answer changes
ScaleDAU, read:write ratio, data size, growth, peak vs average?Single node vs partitioned; cache and replica count
Latencyp99 target for the hot path? Is it user-facing or batch?Sync vs async, caching, precomputation, region placement
AvailabilityTarget nines? Is degraded service acceptable?Redundancy level, multi-AZ or multi-region, fallbacks
ConsistencyCan a read be stale? For how long? Which operations cannot be?Leader reads vs replica reads, quorum, transactions
DurabilityIs losing an acknowledged write ever acceptable?Sync replication, fsync policy, backups, queue persistence
SecurityWho may call it? Any PII, payments, multi-tenant isolation?AuthN/AuthZ placement, encryption, audit trail
CostIs there a budget or cost-per-request constraint?Storage tiering, compute choice, how much is precomputed
ComplianceData residency, retention, right to delete?Region pinning, deletion pipelines, immutable logs

Interview tip: do not ask all eight. Ask scale, latency and consistency, then propose the rest: "I'll assume 99.9% availability and no acknowledged write is lost; tell me if that is wrong".

Latency numbers

Estimation

Order of magnitude only; they vary by hardware and year. What matters is the ratios: memory is about 1,000x faster than SSD, a network hop inside a datacentre costs about as much as thousands of memory reads, and crossing an ocean costs hundreds of datacentre hops.

OperationTime (order of magnitude)Relative
L1 cache referenceabout 1 ns1x
Branch mispredict / L2 cache referenceabout 3 to 10 ns10x
Mutex lock and unlock (uncontended)about 20 ns20x
Main memory (RAM) referenceabout 100 ns100x
Compress 1 KB with a fast codecabout 2 to 10 us10^4 x
SSD random readabout 100 us10^5 x
Read 1 MB sequentially from memoryabout 10 to 100 us10^5 x
Round trip within the same datacentreabout 0.5 ms5 x 10^5 x
Read 1 MB sequentially from SSDabout 1 ms10^6 x
Spinning-disk seekabout 10 ms10^7 x
Read 1 MB sequentially from spinning diskabout 10 to 20 ms10^7 x
Round trip between continentsabout 100 to 150 ms10^8 x
  • A cache hit over the network (about 0.5 to 1 ms) is dominated by the network, not by the cache.
  • Sequential I/O beats random I/O by orders of magnitude on disk, which is why logs (WAL, Kafka, LSM trees) append.
  • A cross-region synchronous call adds about 100 ms per round trip; keep them off the hot path or pay for it knowingly.
  • Human-perceived "instant" is about 100 ms; a typical API p99 budget is 100 to 500 ms.

Scalability: vertical vs horizontal

Core trade-offs

Scale up (bigger machine) until it stops being cheap or safe; scale out (more machines) when you need capacity beyond one box or redundancy. Scaling out is easy for stateless tiers and hard for state.

 Vertical (scale up)Horizontal (scale out)
GainNo code change, no distributed-systems problems, strong consistency stays easyNear-linear capacity, redundancy, incremental cost
PayHard ceiling, single point of failure, downtime to resize, price grows faster than capacity at the top endLoad balancing, partitioning, coordination, partial failure, operational complexity
Use whenDatabases early on; anything under one node's limitsStateless services always; data tier once one node is not enough
  • Stateless service: any instance can serve any request because session and data live in a shared store or in the request (token). This is what makes load balancing, autoscaling and rolling deploys trivial.
  • Scalability is not performance: a system is scalable if adding resources adds capacity roughly in proportion.

Senior signal: "one large Postgres with a replica handles this for the first two years; I'd shard only when write volume or dataset size forces it" is a stronger answer than sharding on day one.

Latency, throughput and percentiles

Core trade-offs

Latency is time per request; throughput is requests per unit time. Batching and queueing raise throughput and raise latency. Near saturation, latency grows non-linearly, so plan to run at 50% to 70% utilisation.

MetricMeaningUse
p50 (median)Half of requests are fasterTypical experience; hides problems
p951 in 20 is slowerCapacity planning
p991 in 100 is slowerSLOs; heavy users hit it constantly
p99.91 in 1,000 is slowerLarge fan-out systems
AverageSum / countAvoid: one 10 s outlier hides in a 50 ms mean
  • If each backend exceeds its p99 on 1% of calls, a request touching 100 backends is slow with probability 1 - 0.99^100 = 63%. With 10 backends it is about 10%.
  • Tail-latency tools: timeouts with budgets, hedged requests (send a second copy after the p95 delay), partial results, fewer hops, avoiding shared queues.
  • Sources of tail latency: GC pauses, lock contention, cold caches, noisy neighbours, retries, queue build-up.

Interview tip: always quote a percentile: "p99 under 200 ms", never "fast" or "200 ms average".

Availability arithmetic

Core trade-offs

Components in series (all must work) multiply availabilities and make things worse. Components in parallel (any one is enough) multiply failure probabilities and make things better, assuming failures are independent.

StepArithmeticResult
Series ruleA = A1 x A2 x ... x AnThree 99.9% parts in series: 99.7%
Parallel ruleA = 1 - (1 - A1) x (1 - A2) x ...Two 99% parts in parallel: 99.99%
App tier above1 - 0.001 x 0.00199.9999%
Whole path0.9999 x 0.999999 x 0.9995about 99.94%, roughly 5 hours down per year
Add a DB standby with failoverDB becomes 1 - 0.0005^2, in theoryPath is now limited by the LB: about 99.99%
  • Redundancy only helps if failures are independent: same rack, same AZ, same bad deploy or same poisoned request breaks the assumption.
  • Failover is not instant or perfect; detection time and failed failovers count as downtime.
  • Every hard dependency you add in series lowers your ceiling. Make dependencies soft (cache, default, degrade) where you can.

Failure mode: correlated failure. Most large outages are a config push, a bad deploy or an overload cascade that hits all replicas at once, not independent hardware faults.

Reliability vs availability vs durability

Core trade-offs

PropertyQuestion it answersMeasured byBought with
AvailabilityDoes it answer right now?Successful requests / total; ninesRedundancy, failover, load shedding
ReliabilityDoes it do the correct thing over time, even under faults?Error rate, MTBF, correctness of resultsTesting, idempotency, safe deploys, fault isolation
DurabilityOnce acknowledged, is the data ever lost?Probability of loss per year (for example "eleven nines" for object stores)Replication, fsync, checksums, backups, restore drills
  • Available but not reliable: answers every request, sometimes with wrong or stale data.
  • Durable but not available: data is safe on disk, the service is down.
  • Related terms: fault tolerance (keeps working when a component fails), resilience (recovers quickly), MTTR (mean time to recover). Availability is about MTBF / (MTBF + MTTR), so cutting recovery time is usually cheaper than preventing every failure.

Consistency models as a ladder

Core trade-offs

Stronger models are easier to program against and cost more latency and availability. Pick the weakest model that keeps the product correct, per operation, not per system.

ModelGuarantee in one lineWhen it matters
LinearizableBehaves like a single copy; every operation takes effect at one point in real time, and later reads see itLocks, leader election, unique constraints, balances, inventory decrement
SequentialAll clients see the same single order of operations, but that order may lag real timeReplicated logs, state machines fed from an ordered log
CausalOperations that are causally related are seen in order by everyone; concurrent ones may differComment threads (reply never appears before its parent), collaborative apps
Read-your-writesA client always sees its own earlier writesProfile edit then reload; post then view own timeline
Monotonic readsA client never sees time go backwards across successive readsPagination and refresh across replicas with different lag
EventualIf writes stop, all replicas converge; no bound on when, no ordering promise meanwhileLike counts, view counts, DNS, caches, search indexes
  • "Strong consistency" in interviews nearly always means linearizable reads and writes on one object. Serializability is a different axis: isolation of multi-object transactions (see Data Systems).
  • Cheap ways to get session guarantees on an eventually consistent store: read from the leader for a short window after a write, sticky routing to one replica, or pass a version token and wait for the replica to catch up.

CAP and PACELC

Core trade-offs

CAP, stated precisely: when a network partition separates replicas, a system must choose between consistency (C, meaning linearizability) and availability (A, meaning every non-failed node answers). It is not "pick two of three": partitions are not optional, so the real choice is C or A during a partition. PACELC adds the everyday case: else (E), with no partition, you still trade latency (L) against consistency (C).

ClassBehaviourCommonly cited examples (depends on configuration)Fits
PA / ELAlways writable, low latency, reconcile laterDynamo-style stores such as Cassandra with low consistency levelsCarts, feeds, telemetry, session data
PC / ECConsistent always; pays latency, loses availability on the minority sideConsensus-based stores: Spanner-style databases, etcd, ZooKeeperMoney, inventory, metadata, coordination
PC / ELFast when healthy, refuses rather than diverges when partitionedLess common; some single-leader setups with async replicas and strict failoverSystems that prefer downtime to split brain
PA / ECConsistent when healthy, stays up by relaxing consistency under partitionSome configurable storesRarely a deliberate target
  • Many stores are tunable per request (consistency level, quorum size), so classify the configuration, not the product.
  • CAP's "available" is stricter than SLA availability, and its "consistent" is unrelated to the C in ACID.

Interview tip: do not say "this is a CP system" and stop. Say which operation needs which: "placing an order is CP; browsing the catalogue is AP and may be seconds stale".

Read-heavy vs write-heavy

Core trade-offs

The read:write ratio is the first number that shapes a design. Read-heavy systems move work to write time (precompute, cache, replicate). Write-heavy systems move work off the write path (append, buffer, batch, partition).

 Read-heavy (for example 100:1)Write-heavy (for example 1:10)
ExamplesFeeds, product pages, URL redirects, profilesMetrics, logs, IoT, click streams, chat messages, location pings
Main toolsCache, CDN, read replicas, denormalised read models, indexesAppend-only log, queue buffering, batching, sharding, LSM storage
Storage biasB-tree, many indexesLSM-tree, few indexes
You payStaleness, invalidation complexity, slower writesRead-time work (merge, aggregate), eventual visibility
Watch forCache stampede, replica lag, hot keysBackpressure, hot partitions, compaction stalls

Single-leader vs multi-leader vs leaderless

Core trade-offs

Where writes are accepted decides whether conflicts can exist. Details (replication lag, quorums, conflict resolution) are in Data Systems and Distributed Systems Patterns.

 Single-leaderMulti-leaderLeaderless
Writes go toOne nodeAny leader, usually one per regionAny replica; W of N must acknowledge

1 and 2: one box, then a separate database

Scaling step by step

  • Good for: a few hundred requests per second with vertical scaling. Many products never need more than step 2 plus backups.
  • Trigger to move on: the app server is CPU-bound, or any deploy or crash is an outage.

3: load balancer and stateless app tier

Scaling step by step

  • Gain: horizontal app capacity, rolling deploys, health-checked failover. Run the load balancer itself as a redundant pair.
  • Trigger to move on: the database is now the bottleneck, usually on reads first.

4: read replicas

Scaling step by step

  • Gain: read capacity and a promotion target if the primary fails.
  • Failure mode: read-after-write returns stale data. Route a user's reads to the primary briefly after their own write.
  • Trigger to move on: the same queries repeat, or replicas keep being added for a few hot rows.

5: cache

Scaling step by step

  • Gain: sub-millisecond reads for hot data and an order of magnitude less database load.
  • Pay: staleness and invalidation. The database must still survive a cold cache. Patterns and failure modes are in Building Blocks.
  • Trigger to move on: bandwidth and latency for static assets and media.

6: CDN

Scaling step by step

  • Gain: lower latency worldwide, origin offload, absorption of traffic spikes.
  • Media goes to object storage, not app-server disks; uploads use pre-signed URLs so bytes bypass the app tier.
  • Trigger to move on: slow or bursty work (email, thumbnails, fan-out) is making requests slow.

7: queue and workers

Scaling step by step

  • Gain: fast responses, spike absorption, independent scaling and failure isolation of slow work.
  • Pay: at-least-once delivery means handlers must be idempotent.
  • Trigger to move on: the primary database cannot keep up with writes, or the dataset no longer fits one node comfortably.

8: sharding

Scaling step by step

  • Before sharding: bigger primary, archive cold data, split by function (move a table or service to its own database).
  • Choose the shard key from the dominant access pattern; queries that do not include it become scatter-gather.
  • Trigger to move on: users on other continents, or a requirement to survive the loss of a region.
