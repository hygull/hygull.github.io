LLD Case Studies

Ten low-level designs that come up again and again, each worked through the same four steps: requirements, design, runnable code, extensions. Each case is sized for a 45 to 90 minute round: the core is complete and runs, the rest is named and placed. The method, UML notation and concurrency tools are on Low-Level Design; pattern mechanics are on Design Patterns. All code is Python 3.9, standard library only, and every demo is deterministic.

Parking lot

Part 2 of 12 · entities, allocation, pricing

A multi-floor lot with spot sizes issues a ticket on entry, finds the nearest free spot that fits, and charges on exit. It tests whether your entities carry behaviour and whether "nearest" has a data structure behind it.

  • Requirements
  • Design
  • Code
  • Extensions and follow-ups

Parking: requirements

Parking lot

  • Functional: park a vehicle and get a ticket; leave with the ticket and pay; refuse when no spot fits.
  • Rules: motorbike fits small or larger, car fits medium or larger, truck fits large only. Prefer the smallest size that fits, then the nearest spot.
  • Constraints: a few thousand spots, several entry gates (so allocation is concurrent), fee by duration and vehicle kind.
  • Out of scope: payment methods, reservations, sensors, display boards, multiple lots.

Parking lot

Concurrency: several gates call park at once. Pop-from-heap plus ticket insert is a check-then-act: guard park and leave with one lock in the lot (the work inside is microseconds). Across many lots, the source of truth moves to a database row per spot with a conditional update.

  • Why not store is_free on the spot? Then "find nearest free" is a scan; keeping the free set in the allocator makes the query cheap and the spot immutable.
  • Why a frozen Spot? It is shared by the heap and tickets; immutability means neither can corrupt the other.
  • How do you test pricing? Unit-test strategies alone with plain numbers; the lot test only checks the right strategy is called.
  • Where do floors with different rates go? Pricing takes the Spot as well; the interface widens, callers do not change.

LRU cache, then LFU

Part 3 of 12 · O(1) data structure design

A fixed-capacity cache with O(1) get and put that evicts the least recently used key; then the least frequently used variant. It tests whether you can combine two structures so each covers the other's weak operation.

  • Requirements
  • Design
  • Code
  • Extensions and follow-ups, including LFU

LRU: requirements

LRU cache, then LFU

  • Functional: get(key) returns the value or a miss; put(key, value) inserts or updates; at capacity, insert evicts the least recently used key.
  • Constraints: both operations O(1) average; capacity at least 1; "use" means a get or a put.
  • Out of scope: TTL, size in bytes, persistence, distribution.
AskAssumed
Does updating a key count as a use?Yes: it moves to most recent
What does a miss return: None, -1, an exception?None; a miss is an expected outcome, not an error
Can I use OrderedDict?Write it by hand first; show the shortcut after
Called from several threads?Discuss; code single-threaded

LRU: design

LRU cache, then LFU

A dict gives O(1) lookup but no order; a list gives order but O(n) removal from the middle. A doubly linked list keyed by a dict of nodes gives both.

OperationStepsCost
get hitdict lookup, unlink, push frontO(1)
put existingupdate value, unlink, push frontO(1)
put new at capacityunlink head.prev, delete its key from the dict, insertO(1)

LRU: code

LRU cache, then LFU

  • The node stores its key so eviction can delete the dict entry; forgetting this is the most common bug.
  • __slots__ on Node cuts per-entry memory; with millions of entries that matters.
  • OrderedDict is itself a dict plus a doubly linked list in CPython, so the shortcut has the same complexity.

LRU: extensions and follow-ups

LRU cache, then LFU

LFU: evict the key with the fewest uses, least recent among ties. Keep key to (value, uses), uses to an ordered set of keys, and the current minimum; a new key always resets the minimum to 1.

New requirementChange
Per-entry TTLStore expiry in the node; treat expired as a miss on get (lazy), optionally a min-heap of expiries for active cleanup
Evict by memory, not countTrack bytes; evict in a loop until under the budget
Pluggable policy (LRU, LFU, FIFO)An EvictionPolicy interface with touch, add, victim (Strategy); the cache keeps the dict
Load on missInject a loader; see the per-key loading discussion on Low-Level Design

Concurrency: get mutates the list, so even reads need the lock. Wrap both methods in one threading.Lock. For heavy contention, shard: N independent caches selected by hash(key) % N, each with its own lock; recency becomes approximate per shard, which is usually acceptable.

  • Why doubly linked? Removing a node from the middle needs its predecessor in O(1).
  • LRU vs LFU? LRU adapts fast to shifting access; LFU protects long-term hot keys but holds stale ones without ageing.
  • Scan resistance? One full scan flushes an LRU; segmented LRU or admission policies (as in some modern caches) avoid that.
  • Is functools.lru_cache enough? For memoising a pure function, yes; it has no explicit put, delete or TTL.

Elevator system

Part 4 of 12 · scheduling, state, simulation

Several cars serve hall calls (up or down at a floor) and car calls (a floor button inside). It tests separating dispatching (which car) from movement (in what order a car serves its stops), and modelling time as discrete ticks.

  • Requirements

Elevator: requirements

Elevator system

  • Functional: hall call assigns one car; car call adds a stop to that car; cars move one floor per tick and open doors at stops; invalid floors are refused.
  • Rules: a moving car keeps its direction while it has stops ahead (SCAN / LOOK); the dispatcher prefers an idle car or one already heading to the caller in the caller's direction.

Concurrency: hall buttons fire from many threads while a controller thread ticks. Common design: buttons only enqueue requests to a thread-safe queue; one controller thread drains it and owns all car state. No locks inside Car, because only one thread ever touches it.

  • Why not nearest car by distance only? A car two floors away heading the other way may take minutes; the penalty models that.
  • Starvation? LOOK bounds waiting to about two sweeps; age requests if a strict bound is required.
  • How to test? Scripted calls plus ticks, assert the event log, as in the demo.

Vending machine

Part 5 of 12 · the State pattern done properly

A machine accepts coins, sells a product, returns change and refuses actions that make no sense in its current state. It is the canonical State pattern question; the trap is making change after you have already committed the sale.

  • Requirements
  • Design
  • Code
  • Extensions and follow-ups

Vending: requirements

Vending machine

  • Functional: insert coins; select a product; receive the product and change; cancel for a refund; machine reports out of stock when empty.
  • Rules: select needs enough money and stock; the sale happens only if exact change can be returned; no coins accepted while dispensing or out of stock.
  • Out of scope: cards, notes, admin UI, telemetry. Restock is named, not coded.
AskAssumed
Can the user buy several items on one credit?No: change is returned after one sale
Can the inserted coins be used as change?Yes, they join the coin box before change is computed
What signals the end of dispensing?A hardware event, modelled as dispensed()

Vending machine

Vending: code

Vending machine

  • Order inside HasMoney.select: check stock, check money, compute change, and only then decrement stock and switch state. A failed change leaves everything as it was.
  • take_change builds a new counter and swaps it in only on success: raise before mutating.
  • Greedy change is optimal for canonical coin systems such as 10/5/2/1 with unlimited coins; with limited counts or odd denominations it can fail where a solution exists, so use a bounded-coin DP if asked.

Vending: extensions and follow-ups

Vending machine

Patterns: State; change-making as a Strategy once there are two algorithms.

Concurrency: one user at a time by construction, but hardware events (coin sensor, motor) can arrive on other threads. Serialise all events through one queue or one lock on the machine; states hold no data of their own, so they can be shared singletons.

  • Why not an enum and if statements? Fine for two or three states; with four states and four actions it becomes a 16-cell table spread through every method.
  • Who owns transitions, state or context? Here, states set machine.state; a transition table in the context is the alternative when transitions must be configured.
  • Why escrow? Inserted coins are not the machine's until a sale; cancel must return exactly those coins.

  • Minimum number of transfers? Finding the true minimum is NP-hard in general; greedy gives at most n - 1 transfers, which is what products ship.

  • Floating point? Never: integers in minor units, with an explicit rule for the remainder.

Movie ticket booking

Part 7 of 12 · holds, expiry, no double booking

Users pick seats for a show, hold them for a few minutes while paying, and get a booking. The question is really about concurrency: two users must never end up with the same seat, and a slow payment must not block everyone else.

  • Requirements
  • Design
  • Code
  • Extensions and follow-ups

Movie booking: requirements

Movie ticket booking

  • Functional: hold a set of seats for a show (all or none); confirm a hold with payment to get a booking; holds expire after 10 minutes.
  • Invariant: a seat has at most one live hold or booking at any time.
  • Out of scope: catalogue and search (movies, theatres, screens), pricing tiers, cancellations, notifications.
AskAssumed
All-or-nothing for multiple seats?Yes: a group wants seats together
Hold duration, and what if payment finishes after it?10 minutes; late payment is refunded
One process or many?One process here; say how it changes with many

Movie booking: design

Movie ticket booking

Movie booking: code

Movie ticket booking

  • The race is real: two threads released together by a Barrier. Which one wins varies; that exactly one wins does not, so the printed output is stable.
  • The check (no live hold or booking covers the seats) and the claim (add the hold) are inside one with self._lock.
  • The clock is injected: "11 minutes later" is now[0] = 601.0.

Movie booking: extensions and follow-ups

Movie ticket booking

Patterns: payment behind an interface (a port; Strategy when several gateways exist); Observer for confirmation messages.

New requirementChange
Seat categories and pricesSeat value object with a category; a PricingStrategy per show
Cancellation and refund rulescancel(booking_id) frees seats; refund amount from a policy by time to show
Very popular showsLock per seat, acquired in sorted seat-id order to avoid deadlock, instead of one lock per show
Several app serversSeat rows in a database: conditional update WHERE status = 'free' OR hold_expired, or a unique constraint on (show, seat)

Concurrency: one lock per show is correct and fast for an in-process design because the critical sections are microseconds. The senior points are: no I/O under the lock, re-validate after the slow step, and idempotent payment (charge with a request id so a retry does not double-charge). Python mechanics are in Python Concurrency.

  • Why not lock while paying? Payment takes seconds; every other user of the show would wait.
  • Why not a background thread to expire holds? Lazy expiry on access is simpler and exact; a sweeper only reclaims memory.
  • Optimistic instead? Version per seat and compare-and-set; good when conflicts are rare, retry storms when a show opens.
  • Payment succeeds but the server crashes before booking? Reconcile: a job matches receipts to bookings and refunds orphans.

Rate limiter library

In-memory pub-sub queue

Part 11 of 12 · topics, offsets, redelivery

Publishers append to topics; consumer groups each read every message in order, tracking their own offset, with retries and a dead-letter list for messages that keep failing. It tests delivery semantics and why a log with offsets beats a queue that deletes on read.

  • Requirements
  • Design
  • Code
  • Extensions and follow-ups

Pub-sub: requirements

In-memory pub-sub queue

  • Functional: create topics; publish returns an offset; subscribe a consumer group with a handler; each group receives every message, in order.
  • Delivery: at least once. The group's offset advances only after its handler succeeds; a failing message is retried, then dead-lettered after N attempts.
  • Constraints: publishers and consumers on different threads; a late group can replay from the start.
  • Out of scope: persistence, partitions, retention, network protocol.

Pub-sub: extensions and follow-ups

In-memory pub-sub queue

Patterns: Observer at its core, decoupled in time by the log; Iterator for a pull consumer reading from its offset.

New requirementChange
Parallel consumers in one groupPartitions: a topic is K logs, a key hash picks one; each partition is read by one member, so order holds per key
Retry with back-offStore retry_at per group from an injected clock; skip delivery until then
RetentionDrop log prefix below the smallest committed offset, or by age; groups behind it jump forward
Message filtering per subscriberA predicate on the group; skipped messages still advance the offset
DurabilityAppend to a file per topic and store offsets; replay on start

Concurrency: Topic.append holds a lock so offset assignment and append are atomic; read copies a slice under the same lock. Each group is driven by one worker thread, so its offset needs no lock. A blocking pull would use a threading.Condition to wait for new messages (see the bounded queue on Low-Level Design). This mirrors the log-plus-offsets design popularised by Kafka; a real broker adds partitions, replication and persistence.

  • Exactly once? Not from the broker alone: at-least-once delivery plus idempotent handlers (dedupe by message id) gives effectively-once processing.
  • Queue vs log? A queue deletes on ack and spreads messages across consumers; a log keeps messages and gives each group its own cursor.
  • Slow consumer? With a log it just lags; monitor lag (end offset minus committed) and alert.
  • Poison message? Bounded attempts, then a dead-letter list with the error, so the group moves on.
