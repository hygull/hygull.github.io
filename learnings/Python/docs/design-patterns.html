Python Design Patterns

A design pattern is a named solution to a problem that keeps coming back. Sixteen patterns, each shown in a few lines on the same small bank, with the problem it solves and the shortcut Python gives you. Examples run on Python 3.9 or newer with only the standard library.

The bank we will use

The same two classes as in Design Principles. Save this as bank.py. Every pattern imports from it.

Patterns come in three families:

FamilyAnswersIn this tutorial
CreationalHow are objects made?Factory, Builder, Singleton, Prototype
StructuralHow do objects fit together?Adapter, Decorator, Facade, Proxy, Composite
BehaviouralHow do objects talk and share work?Strategy, Observer, Command, State, Template Method, Chain of Responsibility, Iterator

Factory

Problem: the caller knows the kind of account as a string, from a form or an API, and should not need to know which class that means.

A factory is one function that picks the class and returns the object.

Python shortcut: classes are objects, so a dictionary from name to class replaces the class hierarchy of factories that other languages need.

Builder

Problem: an object has many optional parts and must be valid before anyone uses it. A loan needs an amount and a term, and may have guarantors and insurance.

A builder collects the parts step by step and checks them once in build().

Python shortcut: for most objects, keyword arguments with defaults are enough. Use a builder when construction has steps or validation across several fields.

Singleton

Problem: the whole program must share one object, such as the bank's settings.

Python shortcut: a module is already a singleton. Put daily_limit = 50000 in settings.py and import settings everywhere. Use this pattern sparingly: shared global state makes tests depend on each other.

Prototype

Problem: new objects should start as a copy of a prepared one. Every student account opens with the same balance and perks.

Watch out: copy.copy() is shallow, so both accounts would share one perks list and the travel card would appear on both.

Adapter

Problem: code you cannot change has the wrong interface. The old UPI library wants an ID and paise, while the bank works with people and rupees.

An adapter wraps the old object and translates the call.

Decorator

Problem: add behaviour to an object without changing its class, and allow several additions to be stacked.

A decorator wraps an object, has the same methods, and does something extra before or after passing the call on.

Function decorators

Python has the same idea built into the language for functions, written with @.

Facade

Problem: one task needs several subsystems in the right order. A transfer must pass KYC and fraud checks, move the money and write the ledger.

A facade gives callers one simple method and hides the steps behind it.

Proxy

Problem: control access to an object. A debit card stands in front of the account and lets a withdrawal through only with the right PIN.

Proxy or decorator? Both wrap an object. A decorator adds behaviour. A proxy decides whether, when or how the real object is reached: permissions, caching, lazy loading.

Composite

Problem: treat one item and a group of items the same way. A family's money is a tree: the family holds groups, and groups hold accounts.

Give the group the same balance attribute as a single account, and let it add up its children.

Strategy

Problem: one job can be done in several ways, and the choice is made at run time. Interest can be simple or compound.

Put each way in its own interchangeable piece and pass in the one you want.

Python shortcut: functions can be passed around like any value, so a strategy is usually a plain function. Use a class when the strategy needs its own settings or several methods.

Observer

Problem: when something happens, several other parts need to know, and the source should not have to know who they are. A deposit triggers an SMS and a passbook entry.

Payoff: adding an email alert is one new function and one line to register it. WatchedAccount does not change.

Command

Problem: you want to queue, log or undo actions. That is impossible while an action is only a method call that has already happened.

Turn each action into an object that knows how to do itself and how to reverse itself.

State

Problem: an object behaves differently depending on its condition, and every method is filling up with if self.status == ... checks.

Move the behaviour for each condition into its own class and let the account hold the current one.

State or strategy? The shape is the same. A strategy is chosen by the caller and usually stays. A state changes during the object's life, often by itself.

Template method

Problem: several variants share the same steps in the same order, and differ only in a few of them. Every statement has a header, rows and a footer, whatever the format.

The parent class fixes the order. Subclasses fill in or replace individual steps.

Chain of responsibility

Problem: a request should be handled by the first one able to, and the sender should not need to know who that is. A large withdrawal climbs from teller to manager to director.

Iterator

Problem: let callers loop over a collection without knowing how it is stored inside.

Python builds this into the language: define __iter__ and the object works in for loops, sum(), list() and comprehensions.

Which pattern to pick

Start from the problem, not from the pattern.

Remember KISS and YAGNI: a pattern is worth its extra classes only when the problem it solves is really there. If a plain function does the job, use the function. See Design Principles.
